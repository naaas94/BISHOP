## ops — named-volume migration proposal + WAL concurrency adversarial test — 2026-09-11

- **Named-volume migration (OPEN-007 follow-up): design + tooling landed, live cutover not performed.** Windows Docker bind-mount + SQLite WAL + mmap remains a known-bad combination independent of the pool-leak fix above — this closes the residual risk. Full case, chosen architecture, exact `docker-compose.yml` diff, step-by-step cutover runbook and rollback plan: `.dev/decision-logs/ops/sqlite-named-volume-migration.md`. `scripts/sqlite_snapshot.py` and `scripts/sqlite_restore.py` gained a `--volume NAME` mode that reuses the same integrity-gated backup/restore logic inside a throwaway `docker run --rm` container mounting the named volume, writing results back to the host-visible `snapshots/` directory (the volume must be mounted read-write even for the read-only SQL connection — WAL readers still need write access to `-shm`). `docker-compose.override.named-volume.yml` is an opt-in overlay moving only the `state-worker`/`query-api` sqlite mount to a `bishop-sqlite` named volume; the base `docker-compose.yml` is untouched and a plain `docker compose up -d` ignores the overlay file. Verified end-to-end against real throwaway named volumes (WAL-resident rows, corrupt-snapshot refusal, compose-up refusal), all torn down cleanly. The cutover itself — stopping the stack, copying data into the volume, bringing it back up — is a manual operator action per the runbook; nothing here touched the live stack or `BISHOP_DATA_ROOT`.
- **WAL concurrency adversarial test (closes most of OPEN-018).** `tests/test_sqlite_wal_concurrency.py` runs 5 real OS-level writer processes (`multiprocessing`, spawn-safe for Windows) plus a concurrent `mode=ro` reader process against one on-disk WAL file — genuine OS scheduling races, not asyncio tasks sharing one loop. The `BEGIN IMMEDIATE` variant is the regression gate: every writer reaches its full commit count, `PRAGMA integrity_check` returns `["ok"]`, no lost or duplicated writes, the reader completes real reads *during* the run, and a hard wall-clock bound fails loudly on a real deadlock instead of hanging. A deferred-`BEGIN` variant is kept as a skip-marked diagnostic: it showed 12–21 client-side retries per run versus 0 for `BEGIN IMMEDIATE`, consistent with the busy_timeout-bypass-on-lock-upgrade mechanism below, but the exact count is schedule-dependent so it isn't asserted as a hard gate. This does **not** claim the Windows bind-mount tearing class is closed — that's an environment property pytest can't fabricate; it proves the application's lock-handling is correct under real concurrent access, and the named-volume migration above addresses the remaining bind-mount-specific risk.
- Verified: `pytest tests/test_sqlite_wal_concurrency.py` (3× run, no flake) and `tests/test_sqlite_named_volume.py` plus the existing snapshot/restore/compose suites (53 passed) against a real Docker daemon, zero leftover test volumes. Full suite via `scripts/run_tests.py`: 129/129 clean.

## ops — bishop.db salvage + integrity gate + snapshot rotation — 2026-09-11

- **Salvage, not Path B.** Second `bishop.db` corruption, different signature from 2026-06-13: valid header after shutdown, 101 `integrity_check` issue lines (torn btree, bad overflow-list lengths, dead `batches` root page). Recovered 1764 `manifest` / 160 `entries` / 69 `batches` / 6 `scraper_state` into a freshly migrated file that passes `integrity_check` at head `m8_001_pre_filter_tier`. **Nothing was re-paid:** 1622 pre-filter decisions, 153 stage-1 summaries, 135 stage-2 scores and all 160 bodies retained. New `scripts/sqlite_salvage.py` merges the `sqlite3 .recover` dump with a fault-tolerant rowid walk and trusts neither alone; `batches` was re-attributed from 69 `lost_and_found` rows by column arity (its root page was torn), matching exactly the 69 `msgbatch_` ids extracted from the file. The walk added zero rows, proving `.recover` was a strict superset and ~136 manifest rows are unrecoverable. 8 column-shifted `entries` rows dropped to a quarantine JSON rather than served (they fail Pydantic and would 500 the route); 7 reset to `RELEVANCE_PASSED` for a free re-scrape, 1 needs re-discovery. All 97 `INDEXED` rows verified present in LanceDB + DuckDB + BM25 with zero orphans, so index stores were kept and **no** row was demoted. In-flight Anthropic batches needed no replay script — restoring the `batches` rows with their `submitted`/`processing` status let batch-poller's existing `startup_scan` re-fetch and apply them, with no re-submission. See `.dev/decision-logs/ops/sqlite-snapshot-and-integrity-gate.md`.
- **Root cause was a code defect, not the bind mount.** `run_retry_sweep` never called `_prepare_conn`, so `dict(row)` raised on a pooled connection that had `row_factory` unset; the sweep had already issued an `UPDATE`, so `async with get_db()` handed the connection back **with its write transaction open**. WAL has one writer, so that connection held the write lock forever: other connections got `database is locked` and the next borrower of that one got `cannot start a transaction within a transaction`, one more poisoned per sweep tick until every route 500'd — while `/health` did no DB I/O and stayed green, in both incidents. Fixed at three layers: `row_factory` set once at pool creation instead of per call site; `get_db()` rolls back any open transaction before returning a connection and discards/replaces it if rollback fails; `_prepare_conn` + rollback-on-failure added to both sweeps.
- **`BEGIN` → `BEGIN IMMEDIATE`** at all five write-transaction sites in `services/state-worker/app/transitions.py`. A deferred `BEGIN` takes no write lock, so the first `UPDATE` must upgrade, and SQLite returns `SQLITE_BUSY` on an upgrade **without honouring `busy_timeout`**. `busy_timeout` alone did not stop the `database is locked` 500s; this did.
- **Observability fix that explains the silence:** `alembic/env.py` called `fileConfig()` with its default `disable_existing_loggers=True`. `run_migrations()` runs in-process at startup, so `app.main`, `app.db` and every `app.routers.*` logger was disabled for the life of the process — the service could not emit an ERROR after boot. Now passes `disable_existing_loggers=False`. Verified: `app.main.disabled` flipped `False → True` across a `run_migrations()` call before the fix.
- **Hardening (OPEN-007):** removed the dead sqlite mount from `batch-poller` (grep-verified it never opens SQLite); `enforce_integrity()` runs as the **first** lifespan action, before Alembic, and refuses to start on a failing check — logging the issue lines, the newest passing snapshot names and `python scripts/sqlite_restore.py --latest` — with no auto-repair and no auto-restore; new `GET /health/db` does real I/O and returns 503 on failure, and the compose healthcheck now targets it so a corrupt DB blocks all 8 dependents instead of letting them crash-loop against 500s (`/health` stays liveness-only); `PRAGMA busy_timeout` on every pooled connection and the migration engine, overridable via `BISHOP_SQLITE_BUSY_TIMEOUT_MS`; integrity pragma selectable via `BISHOP_SQLITE_INTEGRITY_PRAGMA` (`integrity_check` default, `quick_check` allowed). Gate verified against the real artifacts: refuses the quarantined original, allows the salvaged file, treats a missing path as a fresh install without creating it.
- **Snapshots + restore:** `scripts/sqlite_snapshot.py` gates the source first (a corrupt live file must never become "the newest passing snapshot"), copies via the SQLite online backup API from a `mode=ro` connection into a hidden temp file, fsyncs, integrity-checks, then atomically publishes `snapshots/bishop-YYYYmmdd-HHMMSS.db`; failing attempts are deleted; prune enforces a 24h TTL and only ever matches the snapshot glob inside the snapshot dir. `scripts/sqlite_restore.py` refuses when compose is up (exit 2), refuses a snapshot failing integrity (exit 3), preserves the replaced file as `bishop.db.pre-restore-<ts>`, deletes stale `-wal`/`-shm`, and re-verifies the installed file (exit 4). Live filename stays `bishop.db`; no auto-swap while up. Registered on the host as scheduled task `BishopSqliteSnapshot` every 30 minutes via `scripts/register-snapshot-task.ps1`. Verified taking a snapshot while the stack was writing, and that restore refused with the stack up.
- **Live verification:** rebuilt stack, 4-minute run under load with `database is locked`, `cannot start a transaction`, `ValueError`, HTTP 500 and tracebacks all at **zero** (a pre-fix run had produced all of them plus `scraper` exiting 1). Pipeline advanced manifest 1764 → 2114, entries 160 → 183, batches 69 → 80, INDEXED 97 → 145; live `integrity_check` ok afterwards.
