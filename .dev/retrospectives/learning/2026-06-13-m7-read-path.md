# Learning retrospective — m7-read-path

## 1. Task context

**Task:** M7 — Read Path  
**Date:** 2026-06-13 (implementation + audit); DuckDB lock fix and gate-clearing work continued immediately after  
**Produced:** A queryable read surface for BISHOP — `query-api` with RRF fusion over BM25 + dense vectors + optional challenge-hooks channel, read-only DuckDB metadata filtering, SQLite entry detail, Typer `bishop` CLI, minimal HTMX UI, and `verify-m7.sh` as the automated exit gate.

**Why this qualified:** Four architectural subtasks (shared query contracts, BM25 reader with copy-on-write reload, LanceDB/DuckDB readers + query encoder, RRF/problem-shaped orchestration), a new service boundary (read path separate from vector-writer write path and state-worker hub), and the first time the system became *searchable* end-to-end — not just indexable.

## 2. What I now understand that I didn't before

### The read path is a fusion problem, not a retrieval problem

Before M7 I thought of "search" as picking one index and ranking. The spec's design is explicitly **multi-channel**: sparse (BM25 main), dense (LanceDB cosine), and conditionally sparse again (BM25 challenge_hooks for problem-shaped queries). None of these channels share a score scale. RRF (Reciprocal Rank Fusion, k=60) throws away raw scores and fuses **ranks only** — `1/(k + rank)` summed per `source_id`. That means a channel can be weak individually but still contribute if it surfaces unique candidates early in its list.

Practical implication: you don't tune one retriever; you tune **which channels fire**, **in what order filters run**, and **whether inactive channels are omitted from fusion** (channel 3 must not penalize standard queries — omit the empty list, don't pass zeros).

### Three stores, three consistency models

M6 taught me how entries get written. M7 taught me they **age differently at read time**:

| Store | Role at read | Consistency gotcha |
|-------|--------------|-------------------|
| BM25 pickles on disk | In-memory load + periodic COW reload (default 300s) | New dense hits can appear minutes before BM25 sees them |
| LanceDB | Live vector search on table | Missing table → empty channel, not crash (G7) |
| DuckDB mirror | Metadata pre-filter + hit enrichment | Not SQLite; separate file; lock rules are different |

Search is only as fresh as the **slowest channel you care about**. For interactive search that's often BM25 reload lag, not LanceDB.

### DuckDB locking is not SQLite locking

I had mentally filed "DuckDB read_only=True" under the same bucket as SQLite WAL concurrent read. **Wrong.**

On a single DuckDB file:
- Multiple RW connections: OK
- Multiple RO connections: OK  
- **RW + RO simultaneously: not OK**

The live failure mode was brutal and subtle: `GET /search` ran BM25 + LanceDB + embedding successfully, then died on **metadata enrichment** when opening a read-only DuckDB connection — HTTP 500, `/health` still 200. The root cause was vector-writer holding a **process-lifetime** RW connection, not a lock "only during upsert." Idle vector-writer still blocks query-api reads.

`read_only=True` is a **permission flag**, not a **concurrency guarantee**. The fix is connection **lifetime** discipline: open RW only inside `upsert()`, close in `finally`; query-api opens short-lived RO per operation and degrades (skip pre-filter, empty metadata) rather than 500 when writer wins.

The spec prose implying "read_only while writer holds write lock" is misleading for DuckDB — worth treating as a normative correction, not an implementation detail.

### Hub vs query-api read placement was the right argument to win early

Entries live in SQLite; only state-worker mutates hub state. Putting `GET /entries/{source_id}` on query-api with `mode=ro` SQLite keeps the hub as sole writer without inventing a new hub read API. The plan's `aiosqlite` binding was about **non-claiming read semantics**; stdlib `sqlite3` with read-only URI achieves the same behavior. I care about the invariant (no writes, no state transitions), not the async library — though I should have logged the substitution.

UI and CLI must talk to query-api only. Any shortcut to state-worker for search bypasses RRF entirely. That boundary is architectural, not organizational.

### Tokenization is a cross-service contract

BM25 ranks are meaningless if query tokenization diverges from index tokenization. Extracting `tokenize_bm25` into `bishop_shared` and making vector-writer import it is a one-line change with outsized impact. **Index-time and query-time text processing must share one function**, not "look the same in code review."

### Problem-shaped detection is recall expansion, not classification

`is_problem_shaped` uses §16.3 prefix + content heuristics, intentionally broad. False positives widen retrieval (channel 3 activates); the spec accepts that. I was worried about precision; the system is designed for **don't miss challenge-shaped content**, not **don't annoy with extra channels**.

### Pytest in a multi-service Python monorepo has a footgun I didn't respect

Nine services each use `app` as their package name. Importing `services/query-api/app` then `services/ui/app` in one pytest process poisons `sys.modules['app']`. The M7 gate works around this with **subprocess isolation** for models and integration tests. A green `verify-m7.sh` does not mean a green `pytest tests/`. This is environmental architecture, not test flakiness.

### Fixture gates and live gates measure different truths

M7's automated gate seeds M6-style stores in temp dirs and mocks heavy deps — it proves **wiring and contracts**. It does not prove **compose topology under concurrent writers**. Charter G4/G5/G6 (full ArXiv e2e, live embedding quality, enrichment sampling) were deliberately manual. That's a velocity trade: CI stays fast, owner carries integration risk. The DuckDB incident is the bill coming due for deferring live compose smoke across M3–M7.

## 3. Decisions I made and would make again

**Separate read modules in query-api instead of extending vector-writer stores.** Keeps Docker images and failure domains separate; M6 handoff already pointed here. Importing writer code into query-api would have coupled release cycles and hidden the service boundary.

**Metadata pre-filter before channel calls (plan Flag 4).** When DuckDB can narrow candidates, running BM25/dense on the full corpus is wasted work. Empty candidate set short-circuits without touching channels — clean failure path.

**BM25 copy-on-write reload.** In-place mutation during background reload would violate §8.4 G5 atomicity for concurrent readers. Swap frozen snapshots; on corrupt pickle during reload, keep old index and WARN. Matches how you actually operate a read-heavy path against a writer that's persisting atomically.

**Shared `tokenize_bm25` in bishop_shared.** Cheap, correct, prevents the most likely silent rank-drift bug.

**`bishop` as CLI name over spec's illustrative `kb`.** Charter checkpoint language wins over spec examples when they conflict — reduces doc/CI drift.

**RRF_K=60 as a shared constant in `bishop_shared/query_config.py`.** One pin, one test, orchestrator and encoder both import it — no magic number drift across fusion and docs.

**Generalized principle:** When two services touch the same on-disk artifact, the contract is **file format + connection semantics + process lifetime**, not just "we both use DuckDB."

## 4. Decisions I made that I would change

**Deferring live `docker compose` smoke for the fifth milestone in a row.** The pattern (M3–M7: fixture gate passes, live compose manual) felt disciplined — don't block CI on Docker. In practice it hid the DuckDB lock bug until I ran `bishop search` against a real stack. **Better rule:** every milestone that adds a *new cross-service file lock* gets one scripted compose smoke in the gate, even if it's `curl /search` after seeding one entry. Unit tests cannot falsify "two containers, one file."

**Accepting "treat-as-prediction" on DuckDB concurrent access at audit.** The audit correctly noted M6 had a concurrent-read doc, but disposition was waiver not blocker. I had evidence the assumption was shaky (M6 T6 already deferred it). **Better rule:** if M6 deferred the same coupling and M7 reads the same file from a second process, that's not a prediction — it's an inherited open risk requiring a compose falsifier or explicit "known broken until M7.x" in the gate.

**Binding `aiosqlite` in plan prose without caring about sync vs async.** The executor swapped to stdlib sqlite3; behavior was fine, traceability wasn't. **Better rule:** bind invariants ("read-only, no hub writes") not libraries unless async is load-bearing.

**Not naming pytest `app` collision in pre-plan coupling surfaces.** Scout saw nine `app/` trees; didn't grep for `sys.modules` pollution. T8 discovered it at gate design. **Better rule:** pre-plan checklist item — "shared top-level package names across services."

**Recording handoff after audit instead of before.** Worked out same day, but audit archaeology gap was real. **Better rule:** handoff commit is part of T8 closure, not a post-audit chore.

**Underlying error on DuckDB:** I conflated "read-only connection" with "safe concurrent access" because SQLite trained that intuition. DuckDB needs explicit lifetime management.

## 5. Patterns in my own thinking

**I overweighted integration complexity in the HTTP route layer and underweighted infrastructure coupling.** The orchestrator's highest re-plan risk called out SQLite + batch enrichment + three-source joins (the FastAPI routes subtask). That landed cleanly. The pain was DuckDB locks and pytest namespaces — boring infrastructure, not "interesting" API design. I tend to scan for schema surprises in routes and under-scan for **who holds the file descriptor**.

**I trust green CI slices maybe too much when I've personally waived the expensive checks.** Charter G4/G5/G6 manual sign-off felt responsible (don't fake live LLM quality in CI). But I didn't equivalent-discipline compose smoke — same category of "real environment" risk, different treatment.

**The M3–M7 deferral pattern became a default without re-evaluation.** Each milestone rationally deferred live Docker. Stacked together they created a blind spot. Sunk-cost of the pattern ("we've always done it this way") may have reduced urgency on one compose test.

**I was right to push back on extending vector-writer with search** — that would have felt faster in the moment and been wrong at the boundary. Good instinct on service seams.

**Motivated reasoning watch:** "136 tests pass" felt like done. Search worked in isolated integration. I wanted M7 closed before M8 hardening. Live compose failure was emotionally surprising but predictable in hindsight from the coupling surface list.

## 6. Open questions

- **Domain-only search semantics:** When only `domain` is set, BM25 searches the full domain corpus but dense uses LanceDB `where` — is recall asymmetry acceptable long-term, or does domain need a unified pre-filter across all channels?
- **BM25 reload interval vs indexing burst:** During heavy backfill (M8), is 300s reload lag user-visible enough to warrant event-driven reload (watch pickle mtime) instead of polling?
- **Monolithic pytest recovery:** Rename service packages (`query_api` vs `ui_app`)? Namespace packages? Permanent subprocess gates? What's the right program-level fix vs perpetual isolation?
- **G5 live vs fixture embedding quality:** When does MiniLM-on-fixtures diverge enough from real retrieval to invalidate search quality assumptions before backfill?
- **Spec §8.3 DuckDB prose:** Amend normative spec or keep ops note as source of truth? What do future contributors read first?
- **Health check honesty:** Should query-api `/health` reflect store reachability (DuckDB lock state) or stay liveness-only? The 500-on-search / 200-on-health split confused debugging.

---

## 7. Single paragraph synthesis

M7 taught me that BISHOP's read path is a **multi-store fusion system with different freshness and locking rules**, not a single search index — and that the hardest bug wasn't RRF or SQLite schema joins but **DuckDB holding a process-lifetime write lock while query-api assumed read-only meant safe concurrency**. I can ship a tight contract-tested milestone and still fail the first real `docker compose` search if I keep deferring live cross-service falsifiers; fixture gates prove wiring, compose proves physics. The architectural wins (query-api owns reads, shared tokenize, BM25 COW reload, pre-filter before channels) were the right calls and survived contact with reality. The correction I need to internalize: **when two containers share a file, test the lock model in compose, not just `read_only=True` in a unit test** — and treat inherited deferrals from the previous milestone as open risks, not audit footnotes.
