# Learning retrospective — m4-content

## 1. Task context

**Task:** M4 — Content Slice (`m4-content`)  
**Date:** 2026-06-13 (landed); retrospective filed 2026-06-15  
**What it produced:** A runnable `content-scraper` worker that polls `RELEVANCE_PASSED` manifest rows, fetches ArXiv full text via a new `ArxivAdapter.fetch_content` (HTML endpoint with title/abstract fallback), and POSTs either `content` or `failed` to state-worker — creating `Entry` rows at `SCRAPED` with `content_raw` populated and enrichment fields still null.

**Why a learning retrospective:** Two architectural subtasks (ArXiv fetch strategy + cross-service Docker vendoring), a new worker in the pipeline, and a genuinely new integration seam (adapter-layer retries vs state-machine failure routing). This is the first milestone where BISHOP moves from "metadata in manifest" to "body text in entries."

---

## 2. What I now understand that I didn't before

### Two retry layers, not one

BISHOP has **adapter-layer** retries and **state-machine-layer** retries, and they are not the same thing.

The adapter `failure_envelope` retries HTTP calls (429, 5xx) and classifies outcomes into `RetryExhaustedError`, `PermanentFailureError`, `EscalatableError`. When that layer gives up, the content-scraper does not just log — it POSTs `failed` with `state_at_failure: SCRAPE_QUEUED` and an `is_retriable` flag. State-worker then routes to `SCRAPE_FAILED` (retriable) or `ESCALATION_FLAGGED` (not retriable, e.g. 404).

I had been thinking of "retry" as a single concept. M4 made it concrete: **the adapter answers "should we hit the wire again?"** and **the state kernel answers "what processing state should this row be in now?"** Conflating those would break the charter exit gate (retriable scrape failure must land in `SCRAPE_FAILED` with `error_log.is_retriable=1`, not vanish into logs like the discovery scraper does).

### Entry creation is later than I intuitively expected

Discovery puts rows on the manifest. Pre-filter adds provenance. Content scrape is the moment the **`Entry` record is born** — at `SCRAPED`, not at `DISCOVERED`.

That means `content_raw` population and provenance assertion (`assert_pre_filter_provenance`) are coupled at `POST /entries/content`. The manifest row carries M3 provenance; the ingest DTO for `fetch_content` deliberately omits it because the adapter only needs title/abstract/url to fetch text. Provenance enforcement stays on the state-worker side where the manifest row still exists. I was vaguely aware of this from M1 reading, but M4 is where the seam became operational — poll DTO ≠ ingest DTO ≠ entry row, and that is intentional, not sloppiness.

### ArXiv "full content" without PDF parsing is a degradation ladder, not a binary

ArXiv does not expose one obvious "give me the paper body" API in the spec. The landed strategy: try `https://arxiv.org/html/{raw_id}`, strip HTML with stdlib `HTMLParser`, and if that fails, compose `{title}\n\n{abstract}` from fields already on the manifest row.

This is not a hack — it is an explicit **quality ladder**. M4's job is to populate `content_raw` with *something useful*; M5 owns truncation and enrichment quality. Papers without HTML renditions still flow through the pipeline with title+abstract text. The risk is not pipeline breakage — it is enrichment input quality, which is a downstream problem with a downstream owner. That framing stopped me from over-scoping M4 into PDF/LaTeX parsing.

### Python `app` package collision is a real Docker design constraint

Both `services/scraper` and `services/content-scraper` use `app` as their top-level package name. You cannot naïvely COPY both into one image on `PYTHONPATH=/app`.

The landed pattern: worker stays at `/app/app/`, scraper adapter code is vendored as `/app/scraper_app/` with a `sed` rewrite of `from app.` → `from scraper_app.`. Tests mirror the same rewrite into a temp directory. It is inelegant and brittle (dynamic imports of `app.*` would break), but it preserves a single source of truth for `ArxivAdapter` in `services/scraper/` without duplicating code.

I now treat **package name collisions across services** as a first-class architecture question at image-build time, not an import error you fix later.

### Discovery scraper ≠ content scraper (failure reporting)

M2's discovery loop can log adapter failures and move on. M4's content-scraper **must** POST failures to state-worker because the charter exit gate requires observable `SCRAPE_FAILED` rows and `ErrorLog` entries.

Same adapter code, different worker contract. Reusing the adapter layer without reusing the worker's failure-reporting contract would have looked like progress while leaving the state machine blind.

### Integration tests in a multi-`app` monorepo need explicit isolation

Loading content-scraper's `app` and state-worker's `app` in one pytest process causes `sys.modules` shadowing. M4's integration harness saves/restores modules and uses an isolated loader — same pattern as M3.

This is not pytest weirdness; it is the cost of multiple services sharing the convention `python -m app.main`. The fix is structural (subprocess gates in verify scripts, module isolation in integration tests), not "import differently once."

## 3. Decisions I made and would make again

**Split ArXiv `fetch_content` implementation from the content-scraper service build.** The fetch logic lives in `services/scraper/` (adapter source of truth); the worker is greenfield in `services/content-scraper/`. Keeping them as separate executor subtasks forced an explicit vendoring decision instead of burying it inside one diff.

**HTML + stdlib strip + title/abstract fallback.** No new dependencies, testable with mocked httpx, honest about coverage gaps. PDF parsing would have been a scope trap.

**Vendor as `scraper_app/` with sed rewrite rather than duplicating `ArxivAdapter`.** Duplication would have guaranteed drift by M8 when non-ArXiv adapters arrive. The sed approach is ugly but keeps one canonical adapter tree.

**T3 as verification-only, not state-worker amendment.** M1 already landed `assert_pre_filter_provenance`. Re-implementing or extending the hub would have violated the charter's serialized-amendment rule and added risk for no gain.

**Defer live ArXiv and live Docker to manual validation.** Consistent with M2/M3. The integration harness proves state-machine behavior; live HTTP proves ArXiv availability — different falsifiers.

**Generalizable principle:** *Separate "does the state machine behave correctly?" from "does the external world cooperate?"* Mock the second in CI; gate the first strictly.

## 4. Decisions I made that I would change

**Treating handoff/plan §8 as post-audit cleanup instead of part of "done."** Handoff landed one commit after implementation SHA; plan §8 is still a deferred placeholder at HEAD. I knew this was wrong at M3 audit (F-002) and let it repeat. The better rule: **the last executor commit is not the milestone anchor — the first commit where `git show HEAD:handoff.md` and plan §8 resolve is.** I optimized for moving to M5 instead of closing archaeology.

**Letting §2 claim a config test for `STATE_WORKER_URL` without an override test.** Small gap, but it erodes trust in the contract table as a falsifier list. Better rule: if §2 names a test, the test must cover env override or the row must say "default only."

**Integration e2e that mocks `failure_envelope` entirely on the happy path.** State-machine path is proven; the full adapter→envelope→fetch chain is only proven in unit tests. Acceptable for M4 gate, but I would add one integration path that runs real `fetch_content` with mocked httpx before calling M5 "done" in my head — not because audit required it, but because that is where false greens hide.

**Underlying error on handoff repeat:** momentum heuristic ("code is green, ship the next milestone") overrode a known failure mode I had already paid audit cost to identify.

## 5. Patterns in my own thinking

**I overweighted the ArXiv strategy risk and underweighted artifact hygiene.** The plan's adversarial pass flagged T1 (HTML strategy) as highest re-plan risk. That risk did not materialize. The repeat handoff-not-in-HEAD pattern did — and I had seen it one milestone earlier.

**Review-driven workflow shallowens implementation intuition.** I can explain the two-layer retry model now because the audit and handoff forced me to trace it. I did not internalize it during execution the way I would have if I had written `failure_mapping.py` myself. The learning retrospective is doing corrective work the execution phase skipped.

**Trust in orchestrator decomposition was warranted here.** Four subtasks, clear DAG, contracts that mostly survived. I did not need to push back on T1/T2 split or the provenance verification-only T3. The plan's rejected alternatives (merge T1+T2, six-way split) look correct in hindsight.

**Possible sunk-cost signal:** Advancing M5→M7 without fixing plan §8 or re-auditing M4 after handoff commit. The code was fine; the archaeology debt was known and deprioritized. That is rational short-term scheduling and irrational if I claim audit conditions are binding gates.

## 6. Open questions

- **What fraction of ArXiv papers in a real professional feed have HTML renditions?** M4 tests assume fallback works; M5 enrichment quality on fallback-heavy corpora is unknown until live sampling.
- **Is sed-based vendoring sustainable through M8** when multiple adapters and possibly dynamic imports enter `scraper_app`? Alternative: shared wheel package `bishop_adapters` installed in both images — worth modeling before M8.
- **When does title+abstract-only `content_raw` fail the enrichment model silently vs loudly?** G5-style quality gates may need a content-length or source signal, not just non-null `content_raw`.
- **Should content-scraper loop branches on 409 (provenance, invalid_transition) be integration-tested** or is state-worker coverage enough when the loop only logs and continues? I deferred this twice; I still do not have a crisp rule for "router test sufficient vs loop test required."

Worth studying: ArXiv HTML API stability, and how other ingestion pipelines (Semantic Scholar, OpenAlex) handle full-text when no clean HTML exists.

---

## 7. Single paragraph synthesis

M4 taught me that BISHOP's pipeline has a deliberate **two-layer failure model** (adapter HTTP retry vs state-machine failure POST) and a deliberate **DTO boundary** (manifest provenance enforced at Entry creation, not passed through fetch). The hardest engineering problem — vendoring one Python `app` package into another service's Docker image without duplication — was uglier than the ArXiv content strategy, which reduced to "try HTML, fall back to what you already have." The mistake I keep repeating is not technical: I ship green code and defer handoff archaeology, even after audit explicitly names it, because the next milestone's code is more interesting than making `git show HEAD:plan.md §8` tell the truth.
