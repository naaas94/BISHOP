# Learning retrospective — m6-indexing

## 1. Task context

**Task:** M6 — Indexing Slice (`m6-indexing`) · **Date:** 2026-06-13

**What it produced:** The `vector-writer` service — poll `VECTOR_WRITE_QUEUED` entries from state-worker, embed with pinned `all-MiniLM-L6-v2`, write to LanceDB (dense), per-domain dual BM25 indices (main + challenge_hooks pickles), DuckDB metadata mirror (`entries_mirror`), then `POST /entries/indexed`. Shared contracts landed in `bishop_shared/indexing_config.py` and `atomic_persist.py`. Exit gate: `scripts/verify-m6.sh` + G5 fixture retrieval test.

**Why this qualified:** Four architectural subtasks (shared contracts, LanceDB encoder, BM25 store, orchestration-adjacent design), three new storage backends wired into one pipeline, and the first time Bishop's write path touches hybrid retrieval artifacts that M7 will read. This is not a CRUD slice — it's where ingest becomes searchable.

---

## 2. What I now understand that I didn't before

### A write path is really three different consistency models pretending to be one operation

`index_entry` looks like a single function, but each store has different failure semantics:

- **LanceDB:** check-before-write skip on `source_id` — duplicate means "already indexed," not overwrite. Vectors are immutable identity for retrieval quality.
- **BM25:** in-memory corpus + periodic pickle persist under a domain file lock. Partial failure after `add_main` but before `persist()` is recoverable because the entry stays in `VECTOR_WRITE_QUEUED` and retries; duplicate skip on re-entry is safe only if pickles already contain the doc.
- **DuckDB:** `INSERT OR REPLACE` — no explicit exists check needed. Metadata mirror is idempotent by SQL semantics, not application-level skip.

I used to think "idempotent indexing" was one pattern. It's three patterns glued by ordering: LanceDB → BM25 → DuckDB → state transition. The ordering matters because `POST /entries/indexed` only fires after all three succeed; a crash after LanceDB but before BM25 leaves retriable garbage that check-before-write must handle on retry. That's pipeline design, not store API design.

### LanceDB will happily betray you on schema if you let it infer

The explicit PyArrow `float32[384]` schema decision (LanceDB store + embedding encoder work) clicked something: vector DBs are not "just dump JSON." If the first row establishes schema and a later write has a different-length vector or inferred type, you get silent corruption or write failures deep in production. Pinning dimension at table creation is load-bearing for any embedding model contract — especially when M7 query-api will search the same table with a separately instantiated encoder that must agree on 384 dims.

### BM25 for a personal pipeline ≠ BM25 for a search product

Choosing `rank-bm25` (in-memory, pickle, rebuild-from-corpus on load) over `tantivy-py` (on-disk WAL, native index) was the right call for M6 because:

- Bishop already committed to spec §8.4 S4 atomic persistence (temp → fsync → replace) for BM25 files.
- Single-writer `vector-writer` + per-domain file lock matches MVP volume; rebuild-on-load avoids pickling `BM25Okapi` internals across library versions.
- M7's job is *read* reload (copy-on-write swap), not write-time indexing — separating write path (M6) from read path (M7) made the library choice tractable.

What I didn't appreciate until reading the implementation: **dual indices per domain** (main corpus vs challenge_hooks-only) exist because hybrid search in Bishop treats "problem-shaped queries" as a first-class channel, not just a filter on the same index. That's a product decision encoded as two pickles under one lock.

### "Quality gate" can mean plumbing proof or semantic proof — and conflating them is dangerous

The G5 fixture gate uses orthogonal unit vectors assigned by `fixture_dim`, not real MiniLM embeddings of the fixture text. It proves: embed → store → search → top-1 `source_id` map works end-to-end. It does **not** prove: "hybrid retrieval for sparse document graphs" actually retrieves the ArXiv paper about hybrid retrieval when embedded with MiniLM on real enrichment output.

That's a deliberate trade (CI speed, no HF download) but I now see the charter's subjective "intuitively correct" gate as a **second layer** that can't be automated with orthogonal mocks. Fixture green ≠ retrieval quality green. I was vaguely aware of this at plan time; seeing the fixture implementation made the distinction concrete.

### Python microservices with `app` packages are a test architecture problem waiting to happen

Every Bishop service is `services/<name>/app/`. Integration tests that import state-worker and vector-writer in one process permanently shadow `sys.modules['app.config']`. The milestone gate slice passed; the full suite broke. M7 later fixed this with subprocess-isolated verify scripts — which means the *real* lesson is: **import topology is part of the architecture**, not a test annoyance. If I add an 10th service, the collision surface grows unless isolation is designed in from the integration gate subtask, not discovered at audit.

### DuckDB's lock model is not "SQLite but columnar"

M6 deferred "concurrent read_only while writer holds connection" and documented DuckDB as allowing multiple RW *or* multiple RO, not mixed. M7 then hit live `Conflicting lock` when query-api and vector-writer both touched the file. I hadn't internalized that DuckDB file locking is a first-class integration seam — not something you discover only when wiring the read path. The M6 concurrent-read test (RO after writer *releases*) was necessary but not sufficient for co-located services.

## 3. Decisions I made and would make again

**Freeze shared path constants in `bishop_shared` before any store work.** `LANCEDB_DIR`, `bm25_domain_root`, `DUCKDB_PATH` derived from `BISHOP_VOLUME_MOUNTS` meant T2/T3/T4 couldn't drift into hardcoded `/app/data/...` strings. The principle: *cross-service storage layout is a program contract, not a service implementation detail.*

**Reject state-worker hub changes for M6.** `VECTOR_WRITE_QUEUED` poll exemption + check-before-write was enough for single-instance vector-writer. Adding a claim lock would have been spec-tier escalation for throughput I don't have yet. Principle: *don't amend the hub for deployment assumptions you haven't validated.*

**Split stores into parallel subtasks after shared contracts.** Even though execution ran sequentially, the decomposition let each store's kill criteria stay focused (Lance idempotency key, BM25 lock file scope, DuckDB table name). Principle: *orchestration complexity (poll loop) should not be entangled with storage format decisions.*

**`atomic_persist` as shared utility.** One tested implementation for BM25 pickles beats three copy-pasted temp-replace blocks. Principle: *crash-safe file writes are infrastructure, not domain logic.*

**Defer live G5 to manual sign-off with explicit §7 amendment trigger.** Honest about what CI proves vs what charter asks. Principle: *name the verification layer in the plan, don't pretend fixture tests are semantic gates.*

## 4. Decisions I made that I would change

**Trust handoff narrative about full-suite failures without pairwise reproduction.** Handoff said `test_config_env_round_trip` was "not M6-introduced." Audit proved it was — run `pytest test_m6_integration.py` then the config test and watch vector-writer's `app.config` load. Better rule: *any "pre-existing failure" claim requires a before/after SHA or ordered pairwise pytest command in the handoff, not intuition.*

**Let the integration gate subtask ship without `sys.modules` teardown when the same milestone already had the pattern.** `test_vector_writer_loop.py` teardowns `app`; `test_m6_integration.py` didn't. I reviewed the green gate slice and moved on. Better rule: *when adding a cross-service integration harness, grep the repo for `sys.modules` teardown patterns and make it a packet kill criterion.*

**Commit plan artifacts in a separate SHA from implementation.** Worked for audit eventually, but it means no single commit is "M6 complete." Better rule: *implementation + plan + handoff land in one closure commit unless there's a hard reason not to — the split created unnecessary provenance narration.*

**CHANGELOG tier bullets written from memory, not `git show --stat`.** T4 DuckDB work narrated under T5 in CHANGELOG. Commits were right; paper trail was wrong. Better rule: *changelog entries are generated from commit file lists, not from mental model of what "felt like" one subtask.*

## 5. Patterns in my own thinking

**Review-driven shallow confidence.** I validated M6 by watching agents execute and checking the verify script — I did not mentally simulate crash-between-stores retry paths or import shadowing until audit forced it. The indexing logic is correct; my *ownership* of edge cases was thinner than it should have been for architectural-tier work.

**Over-trust in declared gates.** `verify-m6.sh` green felt like "done." But the program's hygiene bar is `pytest tests/`, and I waived F-004 instead of fixing a 10-line teardown before audit acceptance. Familiar pattern: *milestone gate passes, program health deferred* — I've seen this in M3–M5 with live Docker smoke too; M6 repeated it with test isolation.

**Under-weighted test architecture as design.** I spent planning energy on BM25 lock scope and Lance schema (correct) but treated integration test structure as executor detail. It wasn't — it's what broke.

**Reasonable trust in orchestrator adversarial pass.** Predicting T5 orchestration as highest risk was sensible; the plan's hidden-coupling list (poll omits `content_raw`, compose tag, stub graduation) caught real seams. I should have pushed back only on integration harness isolation, not on the store decomposition.

**No sunk-cost on tantivy.** Good — I didn't revisit BM25 library choice mid-execution despite rank-bm25 feeling "small."

## 6. Open questions

- **When does check-before-write without claim lock break?** Second vector-writer instance, or restart overlap during `index_entry` before `POST /entries/indexed` — spec says 30s grace period helps, but I haven't reasoned through duplicate embed work under overlap quantitatively.
- **Real MiniLM retrieval on ArXiv enrichment output:** Does N1 embed text (`title\nsummary\nhooks`) produce intuitive top-1 for the G5 query phrasings on live data? Fixture doesn't answer this. Worth one manual `BISHOP_G5_LIVE=1` session before trusting M7 search UX.
- **BM25 rebuild cost at scale:** `rank-bm25` rebuilds from corpus on each load; at what corpus size does startup reload in M7 become user-visible? No numbers yet.
- **LanceDB `source_id` filter via string interpolation:** Acceptable for pipeline IDs today; when does parameterized filter API become mandatory?
- **Systematic fix for `app` package collision:** Subprocess verify scripts (M7 approach) vs shared test harness with module teardown vs renaming service packages — which is the long-term Bishop convention?

---

## 7. Single paragraph synthesis

M6 taught me that hybrid indexing is not one idempotent write — it's three storage semantics (skip, lock+persist, upsert) sequenced behind a state transition, and the hard part is making retries safe when any step can fail mid-flight. The technical choices (explicit Lance schema, rank-bm25 + atomic pickle, shared path contracts) were sound for a single-writer local pipeline; the gap was verification honesty — fixture G5 proves plumbing not semantics, and Python's `app` namespace turns integration tests into architectural decisions I treated as executor trivia. The compounding lesson: **at architectural tier, the test harness and the closure commit are part of the product, not paperwork around it** — and reviewing agent output without reproducing failure claims is how shallow confidence masquerades as done.
