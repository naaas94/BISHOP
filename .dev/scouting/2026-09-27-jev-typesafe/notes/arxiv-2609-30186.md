## What Jev is asked to do (role)

- **Paradigm:** low-frequency VLM planning + high-frequency lightweight execution; VLM sets local goals; accessibility tree defines executable action space; **Jev** (described as a **fast typed decision model** / **remote typed Decisions service**) **repeatedly selects actions** within that space under one VLM decision when possible.
- **Per step:** program enumerates candidates from current tree; Jev **chooses a candidate ID** or returns **DONE** / **BLOCKED**; after each action, executor re-observes and rebuilds candidates.
- **Inputs to Jev (paper):** textual accessibility tree, current local goal \(g_k\), prior actions in the delegation, executable candidate descriptions — **not** the screenshot; VLM sees screenshot + tree.
- **Output:** one **typed choice** per request; criteria map candidate IDs, DONE, and BLOCKED to descriptions; adapter validates type and ID before execution.
- **VLM side (delegation):** one call emits `delegate` | `finish` | `blocked`, local goal when delegating, optional exact text values \(v_k\); **no** post-delegation summary generated by VLM.
- **Handoff mode in experiments:** `jev_action_history` (without generated post-delegation summary).

Quoted (abstract):

> Jev, a fast typed decision model, repeatedly selects actions within this space.

Quoted (§3.1 / intro):

> Jev, a remote typed Decisions service, chooses an ID or returns DONE/BLOCKED

Quoted (§3.3):

> Each Jev request is one typed choice: its criteria map current candidate IDs, DONE, and BLOCKED to descriptions.

Quoted (§3.3):

> The output space is constrained, but correctness is not guaranteed.

## Task, benchmark, baselines

- **Benchmark:** full **AndroidWorld** task suite; task initialization and **terminal evaluators** (hidden task state / terminal reward kept out of online prompts).
- **Compared systems (only three):**
  1. **Step-wise VLM** — shared general VLM chooses **each** action from observation + history.
  2. **SeeAct-V** — same general VLM for step-wise decisions + **UI-TARS-1.5-7B** to ground selected target (adaptation of published SeeAct-V).
  3. **Jev-Mobile** — general VLM for local goals; **Jev** selects accessibility-tree candidates until control returns.

Paper note: systems share general VLM but differ in execution mechanisms; outcomes characterize **complete systems**, not isolated Jev effect.

## Limitations (paper §8, verbatim)

> Our evaluation concerns mobile tasks in AndroidWorld only. It does not test web interfaces, whose DOM structure, page dynamics, and interaction patterns may place different demands on a decision-model executor. We compare with two baselines, Step-wise VLM and SeeAct-V, but have not tested the Jev-Mobile workflow with Jev replaced by a small VLM; that comparison would clarify whether the observed behavior depends on typed decision-model execution or on the delegated workflow more generally. Jev-Mobile also depends on the Android accessibility tree: a visually apparent target absent from the tree cannot be turned into an executable candidate by the current controller. Its present input path supports printable ASCII text, and long action histories may require compaction.

Other boundary statements (not §8 but load-bearing):

Quoted (§2):

> Its first version uses deterministic candidates from the raw tree. It does not infer missing visual coordinates, repair the UI hierarchy, or compile semantic field-completion rules; those omissions are measured as candidate-coverage or handoff failures.

Quoted (§3.4):

> If a visual target has no executable tree candidate, the VLM can reinterpret the goal but this first version still may not reach the target: it has no coordinate-producing visual fallback.

## Relevance to “Jev as binary gate over title + abstract text” (packet slice)

**What this paper actually evaluates:** multi-step **mobile GUI control** on AndroidWorld — Jev selects among **program-generated candidate action IDs** (+ DONE/BLOCKED) from a **live accessibility tree**, under a **VLM-provided local goal**, with **re-observation after each action**.

**Not in scope of this paper:**

- No task of scoring or gating **title+abstract** (or any static document snippet) with a binary or thresholded decision.
- Jev input is **structured tree + dynamic candidate set + delegation history**, not Bishop pre-filter-shaped `{title, abstract}` text.
- Decision type is **multi-class typed ID selection** (variable candidate count per screen), not a fixed binary relevance label.

**If extrapolating from this paper to a text gate:** evidence here supports **typed constrained choice** and **efficiency vs step-wise VLM** in **GUI execution**; it does **not** report calibration, discrimination metrics, or text-classification behavior. §8 explicitly leaves open whether gains depend on **typed decision-model execution** vs **delegated workflow** alone (no small-VLM swap ablation).

## Other implementation constraints (may affect generalization)

- Current input tool: **printable ASCII text** only (§3.2).
- Long/noisy accessibility trees: possible failure mode (§3.2).
- Character limit on action history → compaction omits older groups (§3.3).
- SeeAct-V baseline uses **UI-TARS-1.5-7B** instead of original **UGround** (§4, §5.1).
